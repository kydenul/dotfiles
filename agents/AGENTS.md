# 全局规则

## 安全红线

- 密钥 / token / DSN / secret 绝不硬编码进可提交的文件（代码、yaml、文档示例）；生产经环境变量或密钥管理服务注入，可提交配置里只写 `${VAR}` 占位。
- 身份只在信任边界（网关 / 入口）注入；下游只信任边界注入的身份，必须拒绝或覆盖外部传入的同名身份头（如 `x-user-*`），且下游端口只暴露在受信内网。
- CORS：`AllowCredentials=true` 与 `AllowedOrigins=["*"]` 不得同时出现。
- 日志 / 出站请求 dump 默认脱敏（Authorization、Cookie、token）；关闭脱敏必须有明确排查理由并写进注释，排查完把日志级别调回。
- 由用户输入拼接的键（锁键、缓存键、路径）必须校验分隔符等特殊字符，防止拼出他人的键。

## 禁止主动创建 Markdown 文档

- 除非用户明确要求（如「写个 README」「生成一份文档」），不要新建任何 `.md` 文件：README、使用指南、API 文档、功能说明、设计总结都不行。
- 需要解释的内容放在对话里或代码注释里；完成功能后可以问一句「需要我写文档吗？」。
- 不受此限：更新仓库已有的文档（分层 `AGENTS.md`、`changelog.md` 等），因为它们本身就是文档体系，应扩展它而不是另起新文件。
- 用户中途取消写文档时立即停止。

## 推送前必须核查并给出部署清单

执行 `git push`（含创建 / 更新 PR）之前必须完成，不得跳过：

1. 通读待推送的全部改动（`git log @{u}..` + `git diff @{u}..`；无上游时对比目标分支），确认没有夹带无关改动、调试代码、密钥。
2. 在对话里给出「部署清单」，逐项写明；没有影响的项也要写「无」，不能省略：
   - **进程 / 服务**：需要重新构建、重启或滚动更新的进程（写具体名称），及先后顺序。
   - **数据库**：迁移 / DDL / 数据订正（给出脚本路径或 SQL）、是否可回滚、是否锁表、需在代码发布前还是后执行。
   - **Redis / 缓存**：新增、变更、废弃的键及前缀，是否需要清理或预热，旧键与新代码是否兼容。
   - **配置**：配置文件、环境变量、密钥的新增 / 修改 / 删除（写键名与取值来源，不写密钥明文），各环境是否都要改。
   - **其他依赖**：消息队列 / topic、定时任务、对象存储、网关路由、第三方回调、依赖版本等。
   - **兼容与回滚**：新旧版本混跑时是否兼容，出问题怎么回滚。
3. 清单有未确认项（不确定是否需要迁移、不知道哪个进程受影响）时先问用户，不要猜着推。
4. 清单发出后再推送；用户明确说「不用清单」时才可省略。
