# Changelog 规范

## 何时写

- 改了公共 API、行为、配置结构或依赖，就在同一次改动里补 changelog 条目；不要攒到发版再补，也不要漏版本（缺条目时从源码 diff 补记，并注明「补记」）。
- 纯测试 / 注释 / 风格改动也记一条，写明「仅测试，无 API / 行为变更」之类，让使用方能判断要不要关心。

## 结构

- 新版本放在最上面：`## vX.Y.Z（YYYY-MM-DD）`。
- 版本下按需使用以下小节（没有就省略），顺序固定：
  1. `### 新增`
  2. `### 变更`（行为变化，使用方可能受影响）
  3. `### 修复`
  4. `### 变更（无 API 影响）`（重构、依赖替换、风格统一）
  5. `### 测试`
  6. `### ⚠️ 破坏性变更`
- 同一版本内追加的修复可用独立小节，如 `### 2026-10-06 代码审查修复（同一未发布版本内）`。

## 条目写法

- 每条以加粗的包名 / API 名开头：`- **\`pkg.Func\`**：……`；行为变化可在加粗前加 `⚠️`。
- 写清楚：动机（以前有什么问题）→ 现在的行为 → 对使用方的影响 / 怎么验证；细节链接到对应的 `AGENTS.md`，不在 changelog 里复制。
- 修复条目写出用户能看到的症状，原样给出报错文本（如 `expected handshake response status code 101 but got 404`），并注明是哪个版本引入的回归。
- 涉及 `go.mod` 依赖增删时写明影响范围（如「仅 import 该包才编译进二进制」）。
- 未经真实环境验证的内容要明说（如「未经真实环境验证」「测试本次未复跑」）。

## 破坏性变更

- 必须单独列入 `### ⚠️ 破坏性变更`，逐条给出：旧 → 新（签名 / 字段 / yaml 键）、受影响的调用方、迁移步骤（直接改法），以及是编译期报错、启动时加载失败还是运行时行为变化。
- 缺省值收紧（如 fail-open → fail-closed）也算破坏性变更，并给出恢复旧行为的方法。
